# 1. Objetivo del proceso

El objetivo de este procedimiento fue migrar la información de la base de datos relacional `SolarPulseIoT`, desarrollada en SQL Server, hacia MongoDB, aplicando técnicas de modelado de bases de datos NoSQL.

No se realizó una conversión directa de cada tabla a una colección independiente. En su lugar, se reorganizaron los datos para aprovechar las características documentales de MongoDB, utilizando documentos embebidos, referencias y agrupaciones de información.

El proceso contempló las siguientes actividades:

1. Identificación de las tablas de SQL Server.
2. Exportación de información mediante archivos CSV.
3. Importación de los archivos en colecciones temporales de MongoDB.
4. Transformación y reorganización de los documentos.
5. Aplicación de patrones de modelado NoSQL.
6. Validación de cantidades, relaciones y cálculos.
7. Preparación del modelo definitivo para su documentación y diagrama.

# 5. Transformación y modelado de datos

Después de importar los datos, se ejecutó el proceso de transformación mediante el script:

`02_transformar_SolarPulseIoT_MongoDB.js`

Este script utiliza operaciones de agregación de MongoDB, principalmente:

- `$lookup`: permite relacionar documentos de diferentes colecciones.
- `$unwind`: permite trabajar individualmente con elementos de arreglos.
- `$group`: agrupa documentos según determinados criterios.
- `$project`: define la estructura de salida de los documentos.
- `$merge`: guarda los resultados en las colecciones finales.

Se utilizaron las colecciones temporales como fuentes de información para construir 14 colecciones definitivas.

La transformación no consistió únicamente en cambiar nombres de tablas. También permitió reorganizar la información, incorporar documentos embebidos y establecer referencias entre colecciones.

## 5.2. Patrones de modelado NoSQL utilizados

Durante la transformación se aplicaron los siguientes patrones:

**Embedding Pattern**

Consiste en almacenar información relacionada dentro del mismo documento mediante objetos o arreglos.

Ejemplos:
- Permisos dentro de `roles`.
- Distribuidoras dentro de `tarifas`.
- Paneles y sensores dentro de `instalaciones`.
- Actividades y presupuestos dentro de `ordenes_mantenimiento`.

**Referencing Pattern**

Consiste en conservar identificadores que permiten relacionar documentos almacenados en otras colecciones.

Se utiliza para mantener relaciones sin duplicar toda la información relacionada.

**Subset Pattern**

Consiste en almacenar un subconjunto de información que se consulta frecuentemente.

Ejemplo:
- `alertas_recientes` dentro de `instalaciones`, que conserva las últimas cinco alertas relevantes.

**Extended Reference Pattern**

Consiste en almacenar la referencia de otro documento junto con algunos datos descriptivos para evitar consultas adicionales.

Ejemplos:
- Información extendida del rol en `usuarios`.
- Información del cliente en `instalaciones`.
- Información de la tarifa y del factor de emisión en `instalaciones`.

También se aplicaron:

**Bucketing Pattern:** agrupa mediciones por sensor y hora, y consumos por instalación y día.

**Computed Pattern:** conserva resultados calculados como promedios, totales y cantidades de registros.

Durante el proceso se aplicaron patrones de modelado NoSQL como Embedding, Referencing, Subset y Extended Reference, además de Bucketing y Computed para organizar las mediciones y los consumos de energía.

Las validaciones realizadas permitieron comprobar la correspondencia de los registros migrados, los documentos embebidos, las referencias y los cálculos almacenados.

Finalmente, se generó un respaldo de las 39 colecciones existentes y se comprobó mediante una simulación que los archivos podían ser reconocidos por MongoDB Database Tools.

**Estado del proyecto:** migración, modelado y validación. Las colecciones temporales se conservan para facilitar la revisión y trazabilidad del procedimiento.
